# PhishDrift — project specification

## Context

- Must be novel versus earlier semesters (which built standard URL classifiers with 2–4 ML algorithms
  on static datasets).
- Deadline: about 3 weeks from 2026-10-02 (confirm exact date and update here).
- The student is comfortable with Python, ML, web and extension development.

## Thesis

Most published phishing detectors report 95–99% accuracy using random train/test splits on old,
balanced datasets. Phishing URLs live for hours or days and attackers adapt, so those numbers
overstate real-world performance. This project measures how much, and tests which fixes help.

Headline result to aim for (fill with real numbers):
"Random-split detectors lose X points of recall on future data; drift-triggered retraining and
multimodal, adversarially hardened models recover Y points and cut evasion from A% to B%,
shipped as an explainable Chrome extension."

## Experiments

### E1 — Temporal drift
1. Train the baseline (URL lexical features, LightGBM) with a random split. Record metrics.
2. Same data, time split: train on older months, test on newer months (domain-disjoint).
3. Rolling evaluation: train on months 1..k, test on month k+1; plot recall@1%FPR over time.
Output: `reports/figures/e1_random_vs_time.png`, `reports/figures/e1_rolling.png`, a table.

### E2 — Adversarial robustness
1. Take phishing URLs the model currently detects in the frozen time-split test set.
2. Apply each attack family in `attacks/`: homoglyph/punycode, subdomain stuffing, brand keyword
   injection, path/query padding and encoding, shortener/redirect wrapping, TLD swap and hyphenation.
3. Evasion rate = flipped to benign / originally detected, per family and combined.
4. Harden: add attacked samples to TRAINING only; hold one family out entirely and test on it.
5. Re-check clean recall and FPR so hardening didn't raise false positives.
6. Benign stress test: long legitimate URLs and real shorteners, to catch over-flagging.
Note: some attacks change domain-level signals (age, cert); document which features each attack can
and cannot realistically alter.
Output: before/after evasion table, `reports/tables/e2_evasion.csv`.

### E3 — Drift-triggered retraining
1. Monitor feature drift on incoming data with PSI (and KS test) per feature.
2. Retrain when drift exceeds a threshold; compare static model vs periodic retraining vs
   drift-triggered retraining over the live-feed period and PhreshPhish's later months.
Output: line chart of recall over time for the three strategies.

### Ablation (ties it together)
Start from URL-only baseline and add one thing at a time, reporting recall at FPR 1% and 0.1% on the
time-split test set:
1. + HTML/DOM features
2. + domain/DNS/TLS features
3. + stacking (GBDT + XGBoost + LightGBM)
4. + adversarial training
5. + calibration and threshold at target FPR
6. (stretch) + brand-vs-domain check

## Model

- Feature-based gradient boosting (LightGBM primary), stacked with XGBoost/GBDT.
- Separate URL model small enough to run in the browser (export to ONNX → ONNX Runtime Web, or
  convert trees to JS). Full model (URL + HTML + domain) runs in the backend.
- Calibrate probabilities (isotonic or Platt). Pick thresholds for "suspicious" and "dangerous" from
  target FPRs, not 0.5.
- SHAP values for explanations, mapped to plain-English reason strings.

## Product architecture

Chrome extension (Manifest V3):
- Service worker: listens to navigations, runs the layered check, caches verdicts per domain.
- Content script: hover/click link checks; page checks (password field on new non-allowlisted
  domain, form action posting to another domain, brand name in title/text not matching domain).
- Warning interstitial for "dangerous", banner for "suspicious", popup with reasons.
- "Report false positive" button that logs to the backend.

Layers, cheapest first:
1. Allowlist (top domains + user-trusted)
2. Blocklist (Google Safe Browsing, prefer hash-prefix lookups; cached OpenPhish/URLhaus)
3. In-browser URL model
4. Backend: RDAP domain age, DNS, TLS cert, redirect chain, full model
5. Page-level checks

FastAPI backend: `/score` (domain + URL features → verdict, reasons), `/domain-info` (cached RDAP/DNS/TLS),
`/feedback`. Per-domain cache, timeouts, rate limits.

## Milestones and acceptance criteria

1. Data ready: collector running daily; PhreshPhish + PhiUSIIL loaded; dedup done; domain- and
   time-split files written; data card documenting sources, dates, counts, class balance.
2. Baseline + E1: URL features with tests; random vs time vs rolling results generated by script.
3. Full model + ablation steps 1–3: HTML and domain features; stacked model; ablation table.
4. E2 done: attack suite with tests; evasion before/after; held-out family result.
5. E3 done: PSI monitoring; three retraining strategies compared.
6. Calibration + thresholds; ONNX/JS export with Python–JS feature parity test passing.
7. Backend + extension working end to end on real sites; reasons displayed.
8. Real-world check: recall on that week's fresh feed URLs; false-positive count from normal
   browsing over a few days.
9. Report, README with screenshots and architecture diagram, demo video.
